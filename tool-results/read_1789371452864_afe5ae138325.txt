    40→    40→## 2. P0 - Launch Blockers (fix before any public traffic)
    41→    41→
    42→    42→> These are ordered: 1-2 are exploit-class security holes, 3 is legal/brand risk, 4-6 are integrity/operations.
    43→    43→
    44→    44→### P0-1 · TOTP second factor is fully bypassable - CRITICAL
    45→    45→`_issue_mfa_challenge` mints `claims={"purpose": "mfa_challenge", ...}` (`auth.py:503`), but `get_current_user` (`auth.py:232-244`) decodes **any** token signed with `SECRET_KEY` and reads only `sub` - it never checks `purpose`. The challenge token is returned in the login JSON body, so an attacker who knows only the *password* calls `POST /auth/login`, takes `challenge_token`, and uses it as `Authorization: Bearer …` against every endpoint (envelope download, SMTP settings, API keys) for its full TTL. **2FA enrollment is currently decorative.**
    46→    46→
    47→    47→```python
    48→    48→# app/api/auth.py - inside get_current_user, after decode_access_token:
    49→    49→purpose = payload.get("purpose")
    50→    50→if purpose and purpose != "session":
    51→    51→    raise HTTPException(401, "Invalid session token")
    52→    52→```
    53→    53→And stamp ordinary session tokens with `purpose="session"`. Alternatively sign challenge tokens with a separate key/audience. Add a regression test: challenge token must 401 on `GET /auth/me`.
    54→    54→
    55→    55→### P0-2 · Every signer receives every other signer's bearer token - CRITICAL
    56→    56→`RecipientOut` includes `signing_token: str` (`schemas.py:233`). `SigningSessionOut.all_recipients` (`schemas.py:309`) and `EnvelopeDetailOut.recipients` are serialized with it - the signing-session endpoint is **unauthenticated** (token-bearer), so holder of one signing link calls `GET /api/signing/{token}`, harvests all co-signers' tokens, and can open/sign/decline **as every other party**, bypassing sequential routing entirely. Any workspace `member` can also harvest all tokens via `GET /api/envelopes/{id}`.
    57→    57→
    58→    58→**Fix:** create `RecipientPublicOut` (name, status, order, signed_at - *no* `signing_token`, *no* `verification_code_hash`) and use it for `all_recipients` and for non-owner envelope views. Owners should receive prebuilt link URLs at most, never raw bearer tokens.
    59→    59→
    60→    60→### P0-3 · Fake "Passkey / Biometric" signing stamps legal documents - CRITICAL (legal/brand)
    61→    61→`handleBiometricSign` (`SigningStudioPage.tsx:351-395`) does `setTimeout(650)` then **draws** "WEBAUTHN / BIOMETRIC PASSKEY CERTIFIED … FIDO2-L2 HW-ASSERTION … SHA-256 ENCLAVE LOCKED" onto a canvas and treats it as the signer's signature. No `navigator.credentials` call exists anywhere. A signature block falsely attesting a hardware-backed WebAuthn assertion on a legally-significant document is a misrepresentation risk (and under EU law can mislead about the assurance level of an AES/SES signature). **Remove the tab or implement real WebAuthn** (`navigator.credentials.create` with `platform` authenticator), and never print certification claims the platform cannot substantiate.
    62→    62→
    63→    63→### P0-4 · 2FA enrollment modal can never succeed - and ships a hardcoded test secret
    64→    64→`SettingsPage.tsx:3846-3923`: the modal renders a **mock QR icon** and the **hardcoded demo secret `"JBSWY3DPEHPK3PXP"`** (lines 3874/3879); the code input binds to `totpInputCode` while confirm submits `totpCode` (always `""`); it also optimistically sets `twoFactorConfigured(true)` *before* the API call. The real enrolment payload (`totpEnrol.secret/qr_base64`, fetched at 704-716) is never rendered. Combined with P0-1, 2FA is broken end-to-end: nobody can enroll, and even a valid enrollment doesn't gate sessions. Fix the bindings, render the real QR/secret, delete the demo secret, remove optimistic state.
    65→    65→
    66→    66→### P0-5 · Arbitrary file read via SPA fallback path traversal - CRITICAL
    67→    67→`serve_spa` (`main.py:148`): `candidate = os.path.join(frontend_dist, full_path)` with no containment. `os.path.join` **discards the base when the second argument is absolute**, so `GET //etc/passwd` (or `..%2f..%2f` sequences) reads arbitrary files from the API container - including `/app/certs/*.p12` and the environment. Live whenever the unified image or engine compose exposes the API directly.
    68→    68→
    69→    69→```python
    70→    70→base = os.path.realpath(frontend_dist)
    71→    71→candidate = os.path.realpath(os.path.join(base, full_path))
    72→    72→if not candidate.startswith(base + os.sep):
    73→    73→    return {"detail": "Not Found"}
    74→    74→```
    75→    75→
    76→    76→### P0-6 · Production signing key is baked into image layers
    77→    77→`COPY backend/certs/ /app/certs/` in both `backend/Dockerfile:22` and the unified `Dockerfile:44`. Every `docker compose build` ships the production P12 (and root CA material) into image layers and build cache on the VPS. Anyone with image/registry/daemon access extracts the document-signing identity.
    78→    78→
    79→    79→**Fix:** delete both `COPY backend/certs/` lines; mount certs read-only at runtime (`./certs:/app/certs:ro`); add a `.dockerignore` containing `*.p12`, `*.key`, `certs/`, `.env`, `node_modules`. Note `issue_signing_cert.py` defaults its output to `backend/certs/` - the two combine into a guaranteed leak path.
    80→    80→
    81→    81→### P0-7 · Mobile scan-to-sign hand-off broken by default deployment
    82→    82→`ConnectionManager` (`ws.py:38-63`) is an in-process dict, but both production Dockerfiles run `uvicorn --workers 2` - two disjoint connection maps. Desktop and mobile land on different workers ~50% of the time and never see each other's `MOBILE_CONNECTED` / `SIGNATURE_CAPTURED` relay. The flagship QR hand-off feature silently fails intermittently today (and the frontend side compounds it - see P1-10 stale closure).
    83→    83→
    84→    84→**Fix (pick one):** run **1 worker** with async concurrency now (simplest correct fix); or fan-out via Postgres `LISTEN/NOTIFY` / Redis pub/sub; or sticky sessions + documented single-worker constraint. Pre-requisite for cloud mode: pub/sub, no exceptions.
    85→    85→
    86→    86→### P0-8 · Concurrent final signers can permanently stall an envelope
    87→    87→`submit_signatures` takes `with_for_update()` on the envelope row (`signing.py:396-398`) **after** recipients/fields were already loaded - the second request proceeds on stale in-memory status (`expire_on_commit=False`), both signers see `all_signed == False`, both set status `"delivered"` → the envelope is never sealed, never e-mailed, stuck forever. There is also no enforcement of `required` fields.
    88→    88→
    89→    89→**Fix:** after acquiring the lock, re-read with `populate_existing=True`; evaluate completion from the fresh snapshot; wrap the whole completion pipeline in the same transaction.
    90→    90→
    91→    91→### P0-9 · CI never runs on main - and doesn't cover the frontend or images
    92→    92→`.github/workflows/ci.yml:5` contains `branches: ain]` (mangled YAML - should be `branches: [main]`), so the push trigger matches no branch. There is also no frontend build job, no docker build, no dependency scanning. Every deploy today is untested code reaching the VPS via `deploy_to_vps.py`.
    93→    93→
    94→    94→**Fix:** restore `branches: [main]`; add jobs: `pytest` (as-is) → `audit_clean_room.py` → `npm ci && npm run build` → build both images → run `verify_signing.py` inside the built API image → `trivy`/`pip-audit`. Make it blocking; require it green before deploy.
    95→    95→
    96→    96→### P0-10 · Signers can write into other signers' fields
    97→    97→`submit_signatures` looks up fields by id only (`signing.py:404-407`) - no `f.recipient_id == recipient.id` check - so signer A can plant text, dates, or a base64 signature image into signer B's fields, which are then flattened into the sealed PDF attributed to B. Also unbounded `signature_data_url` (no size cap → DB/memory DoS).
    98→    98→
    99→    99→**Fix:** `if f is None or (f.recipient_id and f.recipient_id != recipient.id): continue` (or 403); cap data URLs (e.g. 512 KB); enforce `required` fields before completion.
   100→   100→
   101→   101→### P0-11 · Backup chain is unproven end-to-end
   102→   102→`deploy/backup.sh:27-31` hardcodes volume name `docurama_docurama_storage` - Docker silently auto-creates missing named volumes, so a misnamed project **tars an empty directory and exits 0**. Archives are unencrypted plaintext SQL + signed PDFs, stored on the same VPS, **excluding the P12/root CA** (a new VPS means historical seals are unverifiable). `GO_LIVE.md:235` itself admits storage "holds the only copy of every signed document", and the Phase-0 plan's required daily cron + one restore drill were never implemented.
   103→   103→
   104→   104→**Fix:** resolve the real volume via `docker volume ls` and fail if absent; verify `tar -tzf | wc -l` against a floor; encrypt (age/GPG) and rsync offsite; add the certs to the backup set; commit a systemd timer; run and document one restore drill using `deploy/restore.sh` (which is correct - the `GO_LIVE.md:239-245` manual rollback is wrong and should point to it, see P1-18).
   105→   105→
   106→   106→### P0-12 · Deploy tooling commits production infrastructure details
   107→   107→`deploy/deploy_to_vps.py:11-13,38` and `scripts/seed_admin.py:22-26,43,52-53` hardcode VPS IP `212.47.79.52`, `root` SSH, and `-o StrictHostKeyChecking=no` (MITM-able admin path; also printed in `GO_LIVE.md:129,242`). Parameterize host/user/key via env with **no defaults**, use `accept-new`, deploy as an unprivileged docker-group user, and rotate the exposed IP.

   111→   111→## 3. P1 - High Priority (fix within the first post-launch weeks)
   112→   112→
   113→   113→### Security & trust
   114→   114→
   115→   115→**P1-1 · No session revocation, 7-day JWTs.** `security.py:50-66` stateless HS256, no `jti`/version claim; `config.py:53` `ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*7`; logout (`auth.py:818-822`) and password change (`auth.py:481-491`) invalidate nothing. A stolen cookie survives a week and a password rotation. Add a per-user `token_version` column checked in `get_current_user`; bump on password change / TOTP disable; shorten TTL + refresh.
   116→   116→
   117→   117→**P1-2 · Domain verification: token not required + TLS disabled + redirects followed.** `domain_verifier.py:139` accepts a page containing merely the substring `"docurama-verification"`; `:107,132` use `verify=False, follow_redirects=True` (MITM-able; redirect-based SSRF into internal ranges with status reflected). Verification is permanent - never re-checked. Fix: require the exact token, `verify=True`, `follow_redirects=False`, block private IPs (mirror `validate_webhook_url`), add periodic re-verification.
   118→   118→
   119→   119→**P1-3 · Public verify portal leaks PII.** `verify.py:106-120` returns the full audit trail (actor emails, IPs, user agents - `schemas.py:277-282`) to unauthenticated callers, matches on envelope UUID as lookup key, and `verify_by_code` has **no rate limit** while each call runs a pyHanko parse (CPU/network amplifier). Redact the public model (event + name + description only), rate-limit, drop the UUID fallback.
   120→   120→
   121→   121→**P1-4 · Settings API leaks third-party credentials & member escalation.** `GET /settings/sms` returns `row.data` verbatim (`settings_api.py:50-72`) - including Telegram bot tokens and Twilio auth tokens - to any workspace member; `PUT /settings/smtp/account` (`settings_api.py:325-351`) has **no owner/admin role check**, so a member can redirect all outbound mail (containing signing URLs) to their own relay. Redact channel secrets (mirror `smtp_config.redact`); require `owner/admin` on SMTP/channel writes.
   122→   122→
   123→   123→**P1-5 · `verify=False`-free webhook module still allows cleartext + rebinding window.** `webhook_dispatcher.py:62` permits `http://`; DNS is re-resolved at connect time after validation (:111-119) - TOCTOU. Require https, pin the validated IP via custom transport, truncate error text stored in delivery rows.
   124→   124→
   125→   125→**P1-6 · Rate limiting is per-worker, per-IP, in-memory + `FORWARDED_ALLOW_IPS=*`.** `rate_limit.py:15` (slowapi in-memory): limits multiply per worker and reset on deploy; behind nginx all clients share one bucket while a directly-exposed port bypasses them. `.env.example:93` + `docker-compose.yml:36` trust `X-Forwarded-For` from anyone → spoofed IPs land in **audit events and certificates**. Default to the docker bridge range, never `*`; move to a shared store (Redis) for cloud mode; add account lockout/backoff on `/auth/login`.
   126→   126→
   127→   127→**P1-7 · Cloud registration is an open abuse surface.** Cloud mode forces open registration (`config.py:111-117`): 5/min in-memory limit, instant `role="admin"` workspace, 7-day Plus trial, **no email verification**, no captcha → trivial trial-farming and storage-quota abuse. Add verified-email gating before envelopes can be sent + trial hard caps + device/IP heuristics.
   128→   128→
   129→   129→**P1-8 · Bulk send & public template start bypass quotas.** `POST /envelopes/bulk` (`envelopes.py:396-484`): no `check_envelope_quota` (single create has one at :79), **no invitation emails are ever sent**, `token_expires_at` never set → bulk links never expire. `POST /templates/public/{slug}/start` (`templates.py:162-242`): unauthenticated, no rate limit, no quota check, mints tokens and copies PDFs per call - a scripted attacker farms the owner's quota/disk. Enforce quota + expiry in both; rate-limit the public start; unify the three divergent token-minting code paths (`generate_secure_token(32)` vs `dcr_sig_<uuid4>`).
   130→   130→
   131→   131→**P1-9 · Envelope state machine gaps.** `decline` (`signing.py:706-731`) and `delegate` (:740-840) don't check `envelope.status` - a signer can flip a **completed, sealed** envelope to `declined` retroactively, or mint a non-expiring delegated token on it. Guard terminal states; set expiry on every minted token.
   132→   132→
   133→   133→### Reliability & performance
   134→   134→
   135→   135→**P1-10 · WebSocket client: leak + stale closure + no reconnect.** `SigningStudioPage.tsx:203-225`: cleanup `return () => ws.close()` is discarded (socket never closed on unmount/token change); `ws.onmessage` closes over the *initial* `activeModalField` (always `null`) so **the phone-to-field signature hand-off never fills the open field even when the relay works**; no `onclose`/retry. Fix with a `useRef` for modal state + reconnect with backoff + AbortController-style teardown.
   136→   136→
   137→   137→**P1-11 · Synchronous SMTP blocks the event loop (systemic).** `mailer.send_email` is plain `smtplib`, called **directly** from `envelopes.py:223,314`, `signing.py:664,687`, `reminder_sweeper.py:115`, `email_channel.py:38` - one slow SMTP server stalls the whole worker (all tenants) for the timeout × recipients. (`auth.py:741`, `companies.py:506` already use `asyncio.to_thread` correctly.) Centralize one `send_email_async` wrapper and route everything through it; commit per-envelope in the sweeper.
   138→   138→
   139→   139→**P1-12 · PyMuPDF/reportlab run inline on async handlers.** `overlay_fields_on_pdf` (`signing.py:491`), certificate generation (`signing.py:557-608`), `get_pdf_pages_info`/`render_pdf_page_png` (`signing.py:194,227` - the latter with **unbounded `?dpi=`**), `FieldDetector.detect_fields` (`templates.py:134`) all block the loop; large PDFs freeze every other request on the worker. `await asyncio.to_thread(...)` for each; clamp `dpi` 72-300 as `documents.py:127` already does.
   140→   140→
   141→   141→**P1-13 · TSA request has no timeout, and the seal path does network I/O under a row lock.** `crypto_engine.py:286` `HTTPTimeStamper(tsa_url)` - pyHanko's HTTP timestamper doesn't time out by default; a hanging TSA holds the envelope row lock (P0-8 fix) and the signer's request indefinitely. Configure a client timeout; cap OCSP/CRL fetch retries; add a rate limit to public `verify_by_code` which also triggers network fetches.
   142→   142→
   143→   143→**P1-14 · Unbounded uploads on public endpoints.** `verify.py:130-131` copies uploads to temp with no size cap (disk-exhaustion DoS) and `scalar_one_or_none()` on `sha256_original` 500s (`MultipleResultsFound`) for bulk-send documents that share a digest. `stamps.py:71` reads whole file into memory. Cap bytes, stream, use `.first()`.
   144→   144→
   145→   145→**P1-15 · Migration safety across replicas.** `entrypoint.sh:5-9` runs `migrate.py` on every start with **no advisory lock** - 2+ replicas race Alembic (and the adoption path can stamp twice). Wrap `migrate.py main()` in `pg_advisory_lock` (same pattern as `reminder_sweeper.py:32-37`) or run migrations as a one-shot compose service. Also make the adoption path fail fast (exit non-zero) on missing NOT-NULL baseline columns instead of stamping a broken schema (`migrate.py:165-174`).
   146→   146→
   147→   147→**P1-16 · Horizontal scaling blocked by compose/nginx/storage.** `container_name` on all services (`docker-compose.yml:4,28,49`) breaks `--scale`; `nginx.conf:14` caches one upstream IP; `storage_layout.py` stores absolute local paths with no S3/object-store abstraction. Cloud mode is effectively single-host. Drop `container_name`s, use a resolver-based upstream, introduce a storage interface (`accounts/<id>/` keyed) before cloud beta.
   148→   148→
   149→   149→**P1-17 · Containers run as root with no hardening.** No `USER` in any Dockerfile; no `cap_drop`/`no-new-privileges`/`read_only`/resource limits in either compose file; `docker-compose.engine.yml:21` publishes raw uvicorn on `0.0.0.0:3002` (plain HTTP, no TLS). Add non-root users, hardening options, resource limits, bind engine port to `127.0.0.1`.
   150→   150→
   151→   151→**P1-18 · Documented rollback is broken.** `GO_LIVE.md:239-245` pipes a dump into psql without dropping the schema and without `ON_ERROR_STOP` → fails immediately on a populated DB; `deploy/restore.sh:24-25` does it correctly. Point the runbook at `restore.sh`, add `rollback.sh` redeploys `$PREVIOUS_TAG` (upgrade.sh already captures it), and fix `upgrade.sh:18`'s `|| ` double-run fallback and `deploy_to_vps.py:196`'s `rm -rf alembic/versions/*` before extract.

   153→   153→**P1-19 · Healthcheck lies.** `/healthz` always reports `healthy` even when signing is unavailable (no/wrong/expired P12); compose, `restore.sh:49` and `upgrade.sh:22` all gate on it. Add `/readyz` returning 503 when `signing_ready` is false; point gates at it.
   154→   154→
   155→   155→**P1-20 · Observability ≈ 0.** Only one `logging.getLogger` in the backend (`domain_verifier.py:8`); everything else `print()`; no request IDs, no tenant IDs in logs, no Sentry, no `/metrics`, no log rotation (unbounded json-file). Add structured JSON logging middleware (request-id + account-id - tenant host already captured in `tenant_middleware.py:16`), Sentry DSN knob, `prometheus-fastapi-instrumentator`, compose `logging.max-size`.

   390→   390→## 11. Enterprise Admin Panel ↔ Certificates: the "few clicks" free-certificate wizard
   391→   391→
   392→   392→User requirement: *"research how a cloud user can set up the signature certificates for free from the certification organisms in a few clicks in the dashboard."*
   393→   393→
   394→   394→**Research findings (the honest landscape):**
   395→   395→- **QES (qualified, eIDAS highest tier) is never free** - it requires legally-mandated identity proofing (video/in-person) by a QTSP; "free QES" offers are trials (TrustPro) or subscription-platform plays. Any UI promising "free QES in a few clicks" would be false advertising.
   396→   396→- **Genuinely free options that exist today:**
   397→   397→  - **Actalis** (Aruba Group, Italian CA - an EU qualified CA): **free S/MIME person-validation certificates**, 1-year validity, free renewals; can be used for document-signing at AES level. The only widely-known free certificate from an EU trust-listed CA.
   398→   398→  - **Self-generated organizational certificates** via OpenSSL (the repo already ships `scripts/issue_signing_cert.py` with no-overwrite guards and 600 perms) - free, instant, but trust is private (fine for internal counterparties; recipients see "unknown issuer" warnings elsewhere).
   399→   399→  - **Platform-issued seal** (current default): Docurama signs with its own platform cert - 0 clicks, already works; upgrade path = AATL/EUTL-member document-signing certificate for the platform (paid, ~$100-250/yr from SSL.com/GlobalSign/IdenTrust - cheap because *one* cert covers the platform).
   400→   400→- pyHanko's `pyhanko-certvalidator` supports **both AATL and EUTL** validation - so certificates from EU qualified CAs will validate with proper LTV out of the box.
   401→   401→
   402→   402→**Recommended wizard - "Get a signing certificate" (Settings → Certificates):**
   403→   403→
   404→   404→| Path | Clicks | Cost | Assurance |
   405→   405→|---|---|---|---|
   406→   406→| **A. Use the platform seal** (default for cloud) | 0 | included | AES - platform-attested |
   407→   407→| **B.    414→   414→## 12. GDPR & EU Compliance Roadmap
   415→   415→
   416→   416→Current posture (verified): PII stored includes names, emails, **IP addresses + user agents in audit events**, phone numbers (recipients), signature images, password-reset request IPs. Encryption at rest exists only for recoverable credentials + TOTP secrets (Fernet/HKDF - solid); documents and DB are plaintext on the volume. Hosting is a French OVH VPS (good EU start). No erasure/export endpoints, no retention schedules, no DPA/sub-processor list, no consent tracking.
   417→   417→
   418→   418→### 12.1 What the audit found (GDPR-relevant code facts)
   419→   419→- Audit trail exposes IPs/emails to unauthenticated callers via the verify portal (P1-3) - *both* a security and a GDPR leak.
   420→   420→- No right-to-erasure: workspace deletion exists (`companies.py:601-699`) but `users` rows, memberships, and audit-event PII persist with no schedule.
   421→   421→- No data-subject export (Art 15/20) - needed for the cloud product.
   422→   422→- No global exception logging policy; `print()` logs ship emails to stdout (P2-25) - logging is a GDPR surface too.
   423→   423→- Third-party SMS/Telegram channels and (future) chat widgets are sub-processors - none inventoried.
   424→   424→
   425→   425→### 12.2 Roadmap (ordered, mapped to articles)
   426→   426→
   427→   427→1. **Data map + Records of Processing (Art 30)** - 1 document: subjects (customers, signers, verification-portal visitors), data categories (above inventory), purposes, retention, processors (OVH, SMTP provider, SMS gateway, chat widget, TSA). This is the artifact every DPA request asks for first.
   428→   428→2. **Lawful basis & transparency (Art 6/13)** - contract performance for account data; legitimate interest for audit/security logs; consent for chat widget + optional marketing. Publish privacy policy + cookie banner (needed the moment the chat widget lands, §10).
   429→   429→3. **Retention schedule (Art 5(1)(e))** - document the tension honestly: **completed envelopes have evidentiary value and may be retained** (Art 17(3)(b)/(e) exemptions) - but *hash and truncate*: e.g., audit-event IPs pseudonymized after 12 months; verification-portal query logs 30 days; failed/expired envelopes purged after N months. Implement as a sweeper job (infrastructure exists).
   430→   430→4. **DSR endpoints (Art 15/17/20)** - cloud tier: `GET /privacy/export` (JSON/CSV bundle of the requester's data) and `DELETE /privacy/erase` (anonymize user row: name/email → hashed placeholders, keep envelope evidentiary records, redact IPs/UA in their audit events). Selfhost: same endpoints behind owner auth. ~3-4 days including tests.
   431→   431→5. **Encryption at rest (Art 32)** - enable Postgres/disk-level encryption (LUKS on VPS or managed Postgres with encryption), or app-level: Fernet-wrap PDF bytes at rest using the existing `secrets.py` HKDF machinery. Decide by threat model: for cloud, disk encryption + strict volume access is the pragmatic 80%.
   432→   432→6. **DPA + sub-processors** - publish a DPA (cloud mode) with a sub-processor list (OVH, mail provider, SMS provider, chat, TSA, cert issuers); add a sign-up checkbox for the DPA.
   433→   433→7. **Breach process (Art 33/34)** - 72-hour notification runbook: who detects (Sentry/logs, §P1-20), who decides, template notices. One page, but write it *before* launch.
   434→   434→8. **DPIA (Art 35)** - lightweight one: signature biometrics-adjacent data + audit logs = monitoring-grade processing. The fake-WebAuthn issue (P0-3) must die before any DPIA claims biometric authentication.
   435→   435→9. **eIDAS positioning (marketing-legal alignment)** - state plainly in UI/docs what levels are provided: platform seal + verified-identity invitations = **AES**; QES only via QTSP partnership (§11 path D). Never print "FIDO2 certified" style claims (P0-3).
